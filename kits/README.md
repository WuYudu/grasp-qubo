# 成套搬运：编排层的成套收益排序

## 这个项目在做什么

机器人搬东西的时候，有些收益是**不可加**的：一套夹具的两件、一个订单里的三件，只有凑齐了才算数，单独拿一件是零收益。我们把这个性质写成一个二次型，让"先搬哪件"由优化器决定，而不是由一条手写规则决定。

任务族有三条设定：

- **成套收益**：每一对物品必须连续两步抓完，凑成一对得 0.9 分；单独一件只有 0.1 分。
- **非单调依赖**：抓了一件之后，如果下一步没抓它的搭档，搭档立刻倒塌损毁，这一对永久报废。抓到手不等于拿到分。
- **执行前缀**：一次规划执行前 h 步就重新规划（h=2/3），不是把整条计划执行完。

规模：6–10 件、5 步窗口、66–78 个二值变量。

## 编码

变量 `z[i, s]`：物品 i 在第 s 步被抓，`s = T` 表示不抓。

    E(z) = -Σ_i 0.1·z[i,·]
           - 0.9·Σ_(a,b) Σ_s ( z[a,s]·z[b,s+1] + z[b,s]·z[a,s+1] )
           + λ·( 每物体恰一个槽 + 每步至多一件 + 前置 )

成套收益写成相邻两步的负二次项，不需要辅助变量。罚权重从 8 降到 3（按收益量级缩放），可行域因此宽了很多。

## 四个后端

| 后端 | 说明 |
|---|---|
| `greedy` | 按单件分数排序，不知道成套这件事 |
| `greedy_pair` | 手写规则：抓一件之后立刻抓搭档 |
| `sa` | 二次型 + 模拟退火（`dwave-samplers`，CPU） |
| `milp` | 同一目标线性化后精确求解（HiGHS） |

退火采样后加一步**修复**：按槽位顺序取，跳过重复和前置未满足的，得到一条可执行序列。这一步是关键。

## 结果

5 个种子、执行前缀 h=2/3，成套完成率：

| 后端 | N=6 | N=8 | N=10 |
|---|---|---|---|
| 贪心 | 20–40% | 10–30% | 30% |
| 手写成套规则 | 100% | 100% | 100% |
| 二次型 + 退火 | **100%** | **100%** | **100%** |
| 二次型 + 精确解 | 100% | 100%（h=3 有一例 70%） | 100% |

两件事值得记下来。

第一，贪心在这个任务族里不是"稍差"，是每抓一件就顺手弄坏搭档，完成率 10–40%。

第二，二次型后端追平了手写规则，而 `build()` 里没有一行是为成套写的——同一份编码换掉目标系数就能描述别的不可加收益。

## time-to-target

采样预算从 20 read × 200 sweep 加到 640 × 3000，记录完成率与墙钟：

| 规模 | 20×200 | 80×800 | 320×2000 | 640×3000 |
|---|---|---|---|---|
| N=8 | 100% / 0.03 s | 100% / 0.29 s | 100% / 2.10 s | 100% / 6.02 s |
| N=10 | 83% / 0.04 s | 100% / 0.37 s | 100% / 2.18 s | 100% / 7.44 s |

最小档就达标。之前不是这样：同一条阶梯在没加修复时是 33–83% 非单调乱跳，加采样量没用。瓶颈是样本可行性，不是采样量——这对真机同样成立，链断裂和嵌入本质上是同一类问题。

## 跑起来

```
pip install -r requirements.txt
python src/kits.py                                # 四后端 × 三规模 × 两档前缀
python src/sweep_kits.py "greedy,sa,milp" "2" 5    # 指定后端与种子数
python src/sweep_budget.py                        # 采样预算阶梯
```

计数口径：`done/pairs` 是成套完成率，`kill` 是倒塌数，`act` 是动作数。

## 文件


## 边界

- 退火是 CPU 模拟（`dwave-samplers`），不是真机；真机还要过嵌入、链断裂、机时排队。
- 规模只做到 78 个变量，再大需要分解。
- 场景是合成的，物品尺寸与堆叠规则都简化过。
- 精确解有一例 70%（h=3、N=8），原因是计划被真实场景判为不可行后提前收敛，不是求解器错。
