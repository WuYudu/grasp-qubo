# 真实场景下的闭环拣选：实验结果

版本 1.0 ｜ 目录 `realistic2/` ｜ 数据 `results/bench_main.csv` ｜ 图 `figures/`

## 0. 一句话

把场景按机器人真正会遇到的样子做复杂之后（物体形状不规则、抓取要留出指杆通道、感知有噪声、抓取会失败、可以推一下也可以先把挡路的抓走、任务是按清单拣选），

**贪心从"几乎不输"掉到完成率 47%，而两种会提前规划清障的方法都到了 75%。**

也就是说：之前"闭环里贪心 ≈ 精确解"的结论不是普适的，它是场景太干净（没有清障需求）造成的假象。

## 1. 场景比上一版复杂在哪

上一版（`scaleup_rolling/`）里，物体是一堆凸矩形，能不能抓只看"抓取矩形压没压住下面的物体"，分数是几何打分，失败是一次伯努利抽样。这一版按方案里的四条思路逐条加：

| | 上一版 | 这一版 |
|---|---|---|
| 物体 | 凸矩形 | 矩形/梯形/椭圆/带凹的形状，凸包都不是整块（`_shape`） |
| 可抓性 | 抓取矩形与别的物体重叠 | 两只指杆扫过的**通道**（宽 = 开口 + 指厚，长 20 px）碰没碰到东西；碰了就是"被挡"，先清障 |
| 接近方向 | 没建模 | 只能从上方接近（`sin(approach) > 0` 被强制翻上去），所以"上方有没有空间"是真的算的 |
| 感知 | 无 | 位置高斯噪声 σ=2.5、10% 漏检、掩码膨胀 5%（`observe`） |
| 执行 | 成功/失败 | 成功概率随 适配度/被挡数/是否碰到易碎物/质量 变化；失败后可以重试，也可以**推一下**把挡路的物体挪开 |
| 任务 | 尽量多抓 | **按清单拣选**：8 个指定目标，另有 3 个易碎物（碰了扣成功概率），非目标物体有"清障价值" |

## 2. 执行模型和指标

自己写的抽象执行模型，一个 episode 最多 90 个动作、8 次推：

```
观测（带噪声） → 规划一个长度 T=5 的窗口 → 执行前 2 步
  ├ 成功：抓走（目标则计数，非目标算清障），物体堆会沉降
  └ 失败：推一下挡路的，或重试
```

指标：清单完成率、每抓一个目标要几个动作、单次重规划的 p50/p99 墙钟。三种规划器同一份代码、同一批种子：

- `greedy`：每次挑当前能抓、价值最高的那个
- `milp`：窗口内精确解（pulp + HiGHS），同时决定"抓谁、什么时候抓、要不要先清障"
- `sa`：同一个窗口写成 QUBO 用 `dwave-samplers` 的模拟退火采样，取可执行前缀

## 3. 结果（规模 24/40/60 物体，每个规模 3 个种子）

| 规模 | 贪心 | MILP | 退火 SA |
|---|---|---|---|
| 24 物体 | 3/8（38%） | 6.3/8（79%） | 6.6/8（83%） |
| 40 物体 | 4.3/8（54%） | 6.0/8（75%） | 5.6/8（70%） |
| 60 物体 | 4.0/8（50%） | 5.7/8（71%） | 5.7/8（71%） |

全规模合计：

| 规划器 | 完成率 | 动作数 | 每目标动作数 | p50 | p99 |
|---|---|---|---|---|---|
| 贪心 | 47% | 12.4 | 3.40 | 0.11 ms | 0.14 ms |
| MILP 精确 | 75% | 17.7 | 3.08 | 8.1 ms | 34.3 ms |
| 退火 SA | 75% | 15.1 | 2.54 | 19.2 ms | 38.4 ms |

## 4. 三个值得说的点

**一、清障是分水岭。** 上一版里"抓走一个只会放松约束"，所以贪心等于最优。这一版清单里有目标被别的物体压住，只能先抓走挡路的（非目标），而这步是"花钱买未来"。贪心永远只挑当前分最高的，于是要么在推，要么在重复抓已经能抓的；8 次推用完就卡住。规划器会主动安排"先清 A，再抓 B"，完成率差出一倍。

**二、三者在"动作数 vs 延迟"上各有取舍。** MILP 和 SA 完成率一样，SA 的动作数更少（2.54 vs 3.08，因为它一次给多个候选、前缀更短），但单次决策贵一倍多（19 ms vs 8 ms）。贪心便宜三个数量级，代价是完成率腰斩。**如果节拍要求是每步 5 ms 以内，MILP 还能用；1 ms 以内就只能用贪心，并且接受 47% 的完成率。**

**三、感知噪声没有把规划器打崩。** 之前担心"精确解会过度相信噪声、把错误放大"，这一版里没有出现：MILP 的完成率随规模只是从 79% 缓降到 71%。原因大概是每 2 步就重新观测一次，噪声来不及累积。

## 5. 踩的坑（都是几何和编码层面的，写下来省后来人）

1. **指杆通道要"朝上"**。一开始通道从抓取点沿接近方向铺 52 px，结果埋在最下面的物体反而"可抓"（通道扎进箱底）。正确做法是只探测抓取点上方一小段（20 px）是否空：拉太短测不到包裹，拉太长会把上一层的物体全算成阻挡。
2. **这个世界的 y 轴是反的**（cy 越小越高，`above()` 就是这么判的），所以"朝上"要写在 `sin(approach) > 0` 而不是 `< 0`。写反之后可抓物体直接变 0。
3. **互锁不能判成不可行**。窗口模型里前置约束如果对"不抓"那一档也生效，两个互相压住的物体就无解、规划器返回空，episode 只能靠推 —— 一晚上就是这么跑出"35 个动作、0 个收获"的。改成只对真实抓取步生效，环上的物体可以被放弃。
4. **episode 会死循环**。规划器返回的窗口里可能全是被抓过的物体（观测是旧的），执行循环里全部 `continue`、动作数不增加、`while` 条件永远成立。加"这轮一个动作都没做就推一下，推满 8 次收工"才停住。

## 6. 能说什么、不能说什么

能说：

- 场景复杂度（尤其是"要清障"）会改变结论：简单场景贪心够用，复杂场景规划器值两倍完成率。
- 在同一批场景上，模拟退火和精确解打平，但精确解延迟低一半。
- 每抓一个目标 2.5–3.4 个动作，以及 8 ms 级决策延迟，是可以写进论文的工程数字。

不能说：

- 不能说"量子更快"。这里的 SA 是 `dwave-samplers` 的 CPU 模拟，硬件一次没上；而且它和 MILP 打平、更慢。
- 不能说这是真实机器人实验。物体是合成的（`_shape`），执行模型是自己写的抽象模型，不是真夹爪。
- 不能说"真实数据验证过"。这一版**还没接真实数据**，Jacquard 掩码那条线在 `seq2d_repo` 里，是单次抓取用的。
